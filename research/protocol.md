# What would actually qualify?

Checked 22 November 2026. Read the [live task and record table](https://www.hutter1.net/prize/#prev) together with the [detailed rules](https://www.hutter1.net/prize/hrules.htm); use the [FAQ](https://www.hutter1.net/prize/hfaq.htm) for rationale, not as a replacement for the rules. There is no published submission API, mandatory entropy coder or mandatory compressed format. The interface is an exact file transformation, with an accounting rule and resource limits. The [Large Text Compression Benchmark](https://mattmahoney.net/dc/text.html) is a useful comparison, not the award adjudicator.

## Define the experiment

Input is the first 1,000,000,000 **bytes**, not characters, tokens, articles, one GiB, or the contents of today's Wikipedia. Use [Mahoney's distribution and checksums](https://mattmahoney.net/dc/textdata.html): original MD5 `e206c3450ac99950df65bf70ef61a12d`; publisher's SHA-1 `2996e86fb978f93cca8f566cc56998923e7fe581`. Download ZIP size is not the corpus size. UTF-8 XML, redirects, article titles, incomplete document boundaries and escaped markup are material. Do not parse and reserialize XML, convert newlines, Unicode-normalize, remove markup, or silently repair a truncated final record. Reversible transforms are fine; exact restoration, including every exception, is what matters. Benchmark tuning, even rejecting every other input, is explicitly permitted; that does not make an uncounted external dictionary permissible.

## Count bytes before optimizing

* **Self-extracting:** provide `comp9.exe` which takes `enwik9` and emits `archive9.exe`; running the latter in isolation without further input produces `data9` identical to `enwik9`. `S = |comp9.exe or accepted source zip| + |archive9.exe|`. The decoder is already in the archive; don't count it a third time.
* **Separate programs:** compressor `comp9a.exe` makes `archive9.bhm`, `decomp9.exe` restores `data9`. `S = C + 2D + A` for compressor, decoder and raw archive byte counts. If the two programs are the same, the rules allow the `2×` multiplier to become `1×`: total **2C + A**, not `C + A`.
* For the listed executable components, a zip containing source and makefile that builds the executable is an alternative. Necessary compilation/execution options add their lengths to `S`. Do not assume you can submit just a patch against a prior winner, rely on an installed ML stack, or upload only weights and a payload. Include the actual artifact sizes, commands and calculation. Ask judges about ambiguous option counting, system dependencies or nonstandard build steps rather than budgeting zero. C++, Python and assembly are named; other languages are discretionary. Documented source under an OSI-approved license is required for payment even on the executable route. Check all upstream licenses; availability is not permission to redistribute.

For [the listed Ivanov record](https://www.hutter1.net/prize/#prev), `L = 100,424,672`. The [award equation](https://www.hutter1.net/prize/hrules.htm#award) is `500,000 euros × (L−S)/L`, minimum 1%. Integer arithmetic: `S_max = floor(99L/100) = 99,420,425`, a saving of 1,004,247 bytes. The home page's prospective row prints **<99,420,425**; target **99,420,424 or smaller** to satisfy either wording. In practice allow more margin. Getting below 100 MB but above this threshold does not win. Current record is 0.803397376 total bits per input byte; count package bytes, not just model log-loss. `Z` is a constant virtual fund, not one €500k payment or a dwindling account. A sub-1% improvement doesn't change `L`.

## Machine and time: interpret the conflicting summaries conservatively

The [detailed rules](https://www.hutter1.net/prize/hrules.htm#rules) say x86 Linux or Windows, 32- or 64-bit, no additional installations, no outside inputs, standard libraries such as file I/O allowed, no GPU. **Each** program must finish in **less than `70,000/T` hours**, at most 10 GB RAM and 100 GB temporary disk; `T` is the machine's Geekbench **5** score. This is not the sum of encode and decode time. The listed 2021 systems give about 49.05 h for the Lenovo at single-core 1427 and 53.44 h for the Ryzen at single-core 1310; their listed four-/eight-core scores imply about 15.00/8.51 h if applied. Those machines can change. The homepage says roughly 50 h on a single core; the FAQ has older 100-hour and `500,000/T` wording. **Plan for one CPU core; do not infer permission for a multicore design merely from the machine table.** Obtain a ruling on thread count and score selection before depending on either. Do not mix Geekbench versions. Use measured rates on the same accepted winner for calibration; extrapolation is not verification.

## Preflight and submission sequence

1. Build from a clean checkout on the target OS/architecture. Inventory every input on encode, build and decode separately. Anything the decoder 'knows' must be obtainable by an allowed route. Store SHA-256 hashes and exact byte lengths, file inventory, OS, compiler versions/options and license notices. Rebuild a second time to identify packaging drift.
2. Encode from only the original corpus and allowed package. Start decode in a **different empty directory/environment** with just its specified inputs, no original corpus, caches, source tree, network or home-directory models. Give only the verifier access to the reference file. `cmp` the output byte-for-byte; don't treat matching length, text, checksum metadata or program exit status alone as proof. Measure both phases, including preprocessing and writing output. Capture peak memory across all processes and maximum temporary disk footprint, not final directory size. Record cores and Geekbench5, machine/OS, peak space and wall time.
3. Publish freely downloadable artifacts and OSI-licensed documented source, with build/use instructions, algorithm explanation and attribution. Email **all three** recipients on the [participation page](https://www.hutter1.net/prize/hrules.htm#part) its numbered information: direct archive or archive/decoder link; one-line invocation; names, versions and options; package sizes; time/peak main and disk usage; hardware, OS and Geekbench5 score; links to executables or source zip, source, explanatory document and instructions. Agree the division among coauthors before payment. No claim was emailed for this research.
4. Claims are dealt with in submission order, with at least 30 days for public comment and verification. A better submission by the same author within 30 days withdraws the older one. Only the submitted option/version combination qualifies. Committee members have special non-payment and pending-submission rules. Hutter has final discretion, rules may change without notice, and payment is not legally enforceable. Recheck the current record **immediately before filing**. The old per-day discount was temporary; the historical donor [pledge form](https://www.hutter1.net/prize/hpledge.pdf) describes the enwik8/€50k era, not the current terms.
