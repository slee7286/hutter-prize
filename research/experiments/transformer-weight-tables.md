# FX2 transformer: encode quantized weights with one histogram per tensor

## Preregistration, 2026-11-22 UTC — before recoding or histogramming the weights

**Decision.** Test the July `fx2-cmix-T` award-size package. Change only the storage of its int8 tensors whose quantized values are in −7…7. Encode them with a separate fixed probability table per tensor, using its observed counts, rather than the original bit tree that learns from the last few dozen decisions. Everything needed to decode a table is paid for. Do not train a new predictor, reorder articles, change any weight value or touch the corpus payload. This is the strongest cheap bet for a positive net gain, not a prediction of a new prize: the artifact is paid for twice and we can test the entire affected object in seconds. An untested trade-off is whether the current fast adaptation profits more from local variation than it loses from estimation noise.

**Evidence at selection.** At the one status check, the original phda9 decoder had restored all 100,000,000 enwik8 bytes with the reference SHA-256 and exit zero (decoder-only reproduction). No other full verification receipt was present. STARLIT was in ON full encode, not full verification; its five windows predict 320,624 net bytes saved by article ordering, with four favoring ON and one OFF. Neither that predicted gain nor the stored-stream transformer smoke test is a prize result. No running job will be touched. Retuning article order is less decisive on short slices because adjacency is global; changing the predictive model would need CPU-budget and whole-corpus evidence. Neither is required to falsify this storage idea.

**Baseline.** Original published July compressor 3,428,474 B + self-extracting archive 96,996,198 B = 100,424,672 B. Verified on disk: both contain the identical 2,930,652-byte `FX2TFWC2` object. [Release evidence](late-replay.md); [source and model description](https://github.com/astOwOlfo/fx2-cmix-transformer-v1/tree/83f2603f3f7751da5f429fd32669807eb8510494); [prize accounting](../protocol.md). The local exact-weight digest is `7f4db6c8c843a7e6264b6a48ed4805e9e431f543df7a9a0ecb37a35a5e4b8860`. Do not substitute the later fixed build.

**One arm, fixed before measurement.** Use the existing 11-bit binary range-coder precision and tree; transmit 14 little-endian uint16 probabilities per int4 tensor, based on rounded subtree frequencies (clamp to 1…2047; use half for unseen nodes). The fifteenth node splits 14 from impossible 15: its bit is implicit. Keep all other coding decisions unchanged. No choice among several post-hoc encodings. Hypothesis: roughly 0.03 bit/quantized weight on about six million weights gives 22,500 B gross per copy. Allow 8,000 B per copy for tables, framing and incremental executable code: predicted **29,000 net bytes** across both charged artifacts, assuming the corpus stream stays unchanged. This is a working estimate, not a fitted result. Report actual side bytes, change in standalone decoder size, and the exact integrated-code break-even separately; the standalone delta is not the production build delta.

**Decision gate.** Baseline recoding must match the original weight object byte for byte. Both decoders must produce identical tensor names, shapes, dtypes and raw bytes for every tensor (including non-int4). If either fails, no savings claim. If the complete candidate object plus incremental code saves no net bytes, abandon this variant. If positive but small, recommend an integration check, not a fresh billion-byte run. A new full run solely for this idea needs credible coverage of the ~1,004,247-byte prize hurdle or a separate material verification reason. No official score without a compliant integrated build and clean full replay.
